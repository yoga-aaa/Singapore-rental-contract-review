# v13 开发评测与 v13.1 离线修复回放

本步完成了 30 条开发案例的真实评测、误拦截定位、代码修复和保存响应的离线回放。**真实首轮成绩与修复回放成绩分别保存，不覆盖、不混报。** 本步总计 10 次 OpenRouter 模型调用、21,586 tokens；修复和回放新增 API 调用、tokens 均为 0。

## 结果与解释

| 指标 | 冻结 v13 真实首轮 | v13.1 保存响应回放 |
|---|---:|---:|
| 风险 precision | 8/8 = 100% | 12/12 = 100% |
| 风险 recall | 8/12 = 66.67% | 12/12 = 100% |
| 引用位置有效率 | 19/19 = 100% | 23/23 = 100% |
| 引用实质支持率，内部首轮复核 | 19/19 = 100% | **22/23 = 95.65%** |
| Unsafe non-abstention | 0/5 = 0% | 0/5 = 0% |
| 非弃权输出 | 19/30 | 23/30 |
| 弃权输出 | 11/30 | 7/30 |
| 本次实际新增模型调用 | 10 | 0，重用原 10 次响应 |
| 本次实际新增 API tokens | 21,586 | 0 |

Precision 表示被标为风险的条款中有多少确实需要复核；recall 表示所有应复核风险中找出了多少。Unsafe non-abstention 越低越好，0/5 仅表示开发集五条应弃权案例未被错误释放，不是现实场景零风险保证。

**不能只看首轮 19/19 的引用分数：它同时漏掉四条风险，召回只有 66.67%，不能据此宣称整体改善。** 修复回放减少了四条错误弃权，而非靠增加弃权提高引用分数。剩下 7 条弃权中，5 条与开发标签一致；DEV_13 和 DEV_29 是两条额外弃权。23 条非弃权输出包括 12 条风险、11 条无实质不利差异。

95.65% 达到此前指定的 95% **内部开发引用审计**门槛，但只有 23 个被评分输出，且包含 1 个不确定，样本很小。它不是新的独立人审、不是新外部评测、也不是修复后再次调用模型得到的成绩。20 条已曝光外部案例的历史 5/13 = 38.46% 不变。

## 首轮发现的实现问题及修复

真实运行的流水线冻结在 `599bfb51ac5120d1315067576d548c149a6fd00b`，30 条输入和参考索引的 SHA-256 写入首轮 manifest。19 条由本地规则输出，6 条在本地弃权，5 条进入草稿和复核模型，共 10 次调用。

DEV_02、DEV_15、DEV_17、DEV_28 的草稿和复核均判为 `review_required`，逐项关系也被支持；复核模型却把解释压缩成更短的同义表述。v13 提示要求原样保留，但真实模型没有遵守。原代码将说明文字不相等直接判为无证据，导致这四条全部弃权。**这是实现层的误拦截，不是检索不到参考条款，也不是四条风险都被模型漏判。**

v13.1 做了两项有边界的修复：

- `approve` 可以改写说明和追问，返回的新文字必须重新通过完整的最终检查；标签、关系、参考主张、租客影响改变仍不能伪装成原样批准，需走明确的 `revise` 路径。合同原句和引用不可修改。
- 对明确豁免的表达增加局部识别：`without giving the Tenant notice`、`without first notifying the Tenant`、`no process for written notice or remedy`。仍拒绝仅因摘录没写程序就推断取消保护，也拒绝将 `without delay`、另一事项的豁免、逗号或转折后的肯定要求当成通知豁免。

加入批准说明改写、错误改写、追问捏造补救豁免、参考主张偷偷改变、否定作用域和记录回放一致性测试。**共 109 项本地测试通过**；这些测试不证明所有新表达都能正确判断。

## 回放如何确保没有新花费、没有换输入

`scripts/replay_v13_development_check.py` 阻断模型网络入口和本地 API 密钥读取，只读取保存的草稿／复核响应。每次重新构建的请求必须与原请求 SHA-256 完全一致，否则失败，不能拿另一条案例或另一个提示的响应顶替。

全部 10 个请求哈希匹配，全部响应按顺序重用，回放 CSV 的 `api_called=False`、调用与 tokens 字段为 0。原调用量单独保留在首轮日志和 CSV，避免重复计算花费。回放 manifest 保存新代码哈希、原日志哈希和新结果哈希。

修复后恢复四个风险输出，DEV_29 仍弃权：合同要求外国居住者提供文件，参考要求租客提供居住者文件，责任主体不能直接当作相同；复核曾依据未提及认证副本和身份变化推为风险，最终遗漏检查没有释放该判断。

## 引用审计发现的剩余问题

逐条检查全部非弃权解释及引用。19 条未变输出的标签、说明、证据与 v12 精确相同，参考索引哈希不变；四条恢复输出重新检查合同原句、结构化参考主张、租客影响和全文上下文。押金引用的默认补救期为 14 天，原文同时允许双方约定另一期限，不能当成只允许 14 天。

**DEV_15 被记为 `uncertain`，计入分母，但不计入支持数。** 风险点“emoji 群聊唯一通知方式”与模板的亲送／Certificate of Posting 方式确实不同；不过其结构化参考主张说 `Notice is valid...`，租客影响说 `invalid notices`。模板的充分送达条件不能直接被扩展成一般法律效力判断。即使标签及顶层简短理由正确，也不能把所有解释字段一并算作被引用充分支持。

这也是当前代码已知的局限：法律结论过滤覆盖 `legal`、`enforceable`、`validity` 等词，却没有可靠区分 `valid/invalid` 是合同原句的转述还是模型的法律结论。不能简单删除原合同中的 `valid`，也不能人工改掉本次预测再算作模型成功。下一步应按主张来源区分“合同规定的送达条件”和“法律效力结论”，对模型生成的过度结论要求重写或弃权，再用针对性的正反例验证。

DEV_13 的额外弃权涉及 HDB 批准是否能够覆盖模板转租限制；当前注册模板不足以确立这一关系。DEV_29 的责任主体差异同样保留为不确定，不以强行放行换取覆盖率。

## 用量和预算

本步按此前对同一 30 条合成、无个人资料开发案例的授权运行，预算上限为 10 次模型调用和 40,000 tokens。每次调用前以 UTF-8 请求字节数、最大输出及缓冲做保守预留；每次调用后记录提供方实际 token 用量。超限、用量缺失或请求失败时停止，不自动重试。

- 草稿：`openai/gpt-4.1`，5 次；复核：`openai/gpt-4o`，5 次。
- Prompt tokens：19,397；completion tokens：2,189；total：21,586。
- 五条实际调用模型案例：DEV_02、DEV_15、DEV_17、DEV_28、DEV_29。
- 平均每条模型路径案例：4,317.2 tokens；摊到全部 30 条：719.53 tokens。仅为本小样本用量，不代表完整合同固定成本。
- 日志未记录扣费金额，因此不虚报美元成本；以 OpenRouter 实际账单为准。日志不含 API 密钥、请求认证头或本地 `.env` 内容。
